[[stack-start]]
= Voraussetzungen und Start
:page-layout: docs

== Checkouts und Werkzeuge

Schwester-Repositories liegen neben `datenportal-dev-stack`. Die Standardpfade
sind relativ; lokale Benutzerpfade gehören nicht in die Konfiguration.

[cols="2,4",options="header"]
|===
|Repository |Benötigt für
|`../datenportal-themenrepo` |Jeden Stackstart: read-only Quelle für Jenkins; ausserdem Buildvertrag und Initialisierung.
|`../datenportal-jenkins-dev` |Jeden Stackstart: gemountete lokale JCasC. Bei lokalem Jenkins-Build auch Dockerfile, Offline-Bundle und Buildskripte.
|`../datenportal-jenkins-gretl-plugin` |Lokalen Plugin-Build. Entfällt bei ausdrücklich gewähltem Maven-HPI oder vorhandenem HPI.
|`../datenportal-datenblatt-editor` |`--local-editor` und Formular-Browsertest.
|`../datenportal-pilot-daten` |Deklarierte CSV-/XTF-Fixtures für Liefer- und Integrationstests; nicht automatisch publiziert.
|`../datenportal-sodata` |Lokaler Portal-Containerbuild (`--local-sodata`) und Manifest-Integrationstest.
|===

Für jeden Start: Docker mit Compose v2 und laufendem Docker-Daemon, Bash,
OpenSSL und die üblichen Shellwerkzeuge (`sed`, `mktemp`). Für HTTP-Prüfungen
wird `curl` benötigt. `docker compose version` zeigt die installierte Version.

Der empfohlene lokale Jenkins-Build benötigt zusätzlich Git, rsync und Java 17
für das Offline-Bundle. `JAVA17_HOME` kann dessen Erkennung überschreiben.
Maven wird für den lokalen Plugin-Build oder die Maven-HPI-Auflösung benötigt;
der Plugin-Build verwendet Java 21 gemäss
link:https://codeberg.org/edigonzales/datenportal-jenkins-gretl-plugin/src/branch/main/README.md[Plugin-Anleitung].
Mavens JVM muss entsprechend eingerichtet sein (`mvn -version`). Ein explizites
`PLUGIN_HPI_SOURCE` überspringt die HPI-Erzeugung/-Auflösung, aber nicht den
Offline-Bundle- und Image-Build. Der Editor wird mit Node 22 im Docker-Build
gebaut; dafür braucht der Host kein Node. Das Portal wird ebenfalls vollständig
im Docker gebaut (Gradle, npm und WebR; erster Build lädt Abhängigkeiten nach).
Der Host benötigt für beide Containerwege nur Docker; JDK 25 und Node/npm sind
weiterhin für einen manuellen Portal-`bootRun` nötig. Zusätzliche Testwerkzeuge
stehen in xref:entwicklung.adoc[Entwicklung und Tests].

Builds laden Abhängigkeiten und Basisimages. «Offline-Bundle» bedeutet, dass
die anschliessenden GRETL-Läufe ihre Abhängigkeiten lokal auflösen können;
es bedeutet nicht, dass der erste Image-Build ohne Netzwerk möglich ist.

== Empfohlener Entwicklungsstart

[source,bash]
----
./scripts/up.sh --local-editor --local-jenkins --local-sodata
docker compose ps -a
----

`up.sh` führt `init.sh` aus, baut Editor, Jenkins und Portal aus den lokalen
Quellen, initialisiert Garage und den öffentlichen Leseschlüssel und startet
die Dienste. Das aktuelle Datenportal-Plugin wird aus dem Image ins persistente
Jenkins-Volume kopiert; Jenkins wird neu erzeugt. Jobs und Historien bleiben
erhalten. Vor der ersten Veröffentlichung prüft `up.sh` die öffentliche
`current.json`: Bei HTTP 404 bleibt Sodata gestoppt und der nötige Startbefehl
wird ausgegeben. Die nächsten Schritte sind
xref:inbetriebnahme.adoc[Seeder und Initialaufbau].

`init.sh` erzeugt einmalig `.env` mit Schreib- und Browser-Schlüssel sowie
`services/garage/garage.toml` mit Garage-Secrets. Beide Dateien sind ignoriert
und erhalten Dateimodus 600. Vorhandene Dateien werden nicht durch neue
Beispieldefaults ersetzt. Fehlende Browser-Schlüssel können als Paar ergänzt
werden; ein unvollständiges Paar ist ein Fehler. Secrets und bestehende
Garage-Volumes müssen zusammenpassen.

`garage-init` ist ein einmaliger Initialisierungscontainer. `up.sh` führt ihn mit
`docker compose run --rm garage-init` aus und wartet auf seinen erfolgreichen
Abschluss. Der Container wird danach entfernt und erscheint deshalb nicht als
beendeter Container in `docker compose ps -a`. Er stellt den Bucket `ch.so.daten`
bereit und aktiviert dessen Website-Zugriff und CORS. Anschliessend richtet
`up.sh` die Read-only-Rechte des Browser-Schlüssels ein und startet die übrigen
Dienste. Deren konfigurierte Healthchecks müssen erfolgreich sein.

== Startoptionen und Images

[cols="2,4",options="header"]
|===
|Aufruf |Verhalten
|`./scripts/up.sh` |Editor aus Registry. Jenkins- und Portal-Image werden wiederverwendet, sonst gepullt. Nur ein eindeutig fehlender Registry-Tag erlaubt den lokalen Fallback der jeweiligen Komponente.
|`./scripts/up.sh --local-editor` |Editor neu aus dem Schwester-Repo bauen; Jenkins und Portal wie beim Standardaufruf.
|`./scripts/up.sh --local-jenkins` |Jenkins einschliesslich Plugin und Bundle neu bauen, Plugin im Volume ersetzen, Jenkins neu erzeugen.
|`./scripts/up.sh --local-docs` |Dokumentation mit Thoth aus lokalen Working-Trees erzeugen, anschliessend Image bauen. Java 25 und Python mit PyYAML erforderlich.
|`./scripts/up.sh --local-sodata` |Portal-Image neu aus `../datenportal-sodata` bauen und als Container verwenden.
|`./scripts/up.sh --local-editor --local-jenkins --local-sodata` |Empfohlener Weg für den aktuellen Entwicklungsstand aller lokalen Komponenten.
|`./scripts/up.sh --registry-only` |Kein lokaler Jenkins- oder Portal-Fallback. Mit `--local-editor` kombinierbar, mit `--local-jenkins`, `--local-sodata` oder `--local-docs` unzulässig.
|`./scripts/up.sh --help` |Optionen ausgeben, nichts starten.
|===

Ein Registry-Authentisierungs- oder Netzwerkfehler führt zum Abbruch. Beim
Fallback wird ein vorhandenes `datenportal-jenkins:local` beziehungsweise
`datenportal-sodata:local` wiederverwendet; nur wenn es fehlt, wird gebaut.
Ein vorhandenes Image wird nicht automatisch auf neue Registry-Inhalte geprüft.
Solange kein Registry-Image für das Portal veröffentlicht ist, baut der
Standardaufruf den lokalen Stand einmalig. Ein älteres Registry-Editor-Image
muss die Manifestfunktion nicht enthalten; der lokale Build ist der verlässliche
Weg, den aktuellen Checkout zu testen. Die Standardtags und Buildparameter
stehen in xref:konfiguration.adoc[Konfiguration].

Das Portal wird nur gestartet, wenn `current.json` öffentlich mit HTTP 200
erreichbar ist. Danach wartet `up.sh` auf den Container-Healthcheck. Vor der
Erstpublikation bleibt der Container gestoppt; nach der administrativen
Initialpublikation wird der von `up.sh` ausgegebene Compose-Befehl verwendet.
Die lokale Restart-Policy ist auf drei Fehlversuche begrenzt.

`compose.yaml` enthält keine Build-Definition. `docker compose build` allein
baut daher keine Komponenten. Der lokale Editor verwendet
`compose.editor-local.yaml`; Jenkins wird über das Buildskript seines eigenen
Repositories gebaut und mit `compose.jenkins-local.yaml` ausgewählt. Das lokale
Portal verwendet `compose.sodata-local.yaml` und `./scripts/build-sodata-local.sh`;
Dockerfile und Buildlogik liegen in `../datenportal-sodata`.
Bei späteren direkten `up`-/`build`-Aufrufen dieselben Override-Dateien angeben,
sonst kann wieder das Registry-Image gewählt werden:

[source,bash]
----
docker compose -f compose.yaml -f compose.editor-local.yaml \
  -f compose.jenkins-local.yaml -f compose.sodata-local.yaml config --quiet
----

`config --quiet` prüft die aufgelöste Konfiguration ohne Secrets auszugeben.
`ps`, `logs` und `exec` adressieren die bereits laufenden Dienste. Für ein
Update mit HPI-Synchronisierung weiterhin `up.sh --local-jenkins` verwenden;
für den Portalstand `up.sh --local-sodata`.

Die Dokumentation verwendet beim Normalstart das vorhandene Registry-Image
oder zieht es, falls es fehlt. Pullfehler führen zum Abbruch; es gibt keinen
automatischen lokalen Fallback. `--local-docs` baut immer neu und verwendet
`compose.docs-local.yaml`. Die Dokumentation ist bereits vor der ersten
Katalogpublikation unter `/dokumentation/` verfügbar.
